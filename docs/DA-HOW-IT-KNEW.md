# How could Cosmos know “possible” and a list of X?

`python3 scripts/da_machine.py how`

The Cosmos 3-D evolution app is not in this repo. DA cannot
read its source. What DA *can* do is list the only reasons a
program is allowed to say:

- unification is possible,
- there are \(X\) candidates,
- these are harmonic / gauge / topological / … (and more
  types for other dimensional objects),

and then run a reconstructed enumerator that actually emits a
finite \(X\).

The hand is **not** capped at five. Five fingers was a
method. Cosmos already typed more than those five for other
dimensional objects. Extra types stay open
(`p_form`, `moduli`, `characteristic_class`, `spinor`, …).

## How can it know it is possible?

| id | Reason | Needs names? | Needs \(F\)? | Verdict here |
|---|---|---|---|---|
| P1 | \(n>k\) (generic map hits) | no | no | **open** — the clue |
| P2 | existence proof without \(F\) | yes | no | open — not in the repo |
| P3 | write \(F\), \(\chi^2_{\mathrm{ext}}\le\varepsilon^2\) | yes | yes | **fail** |
| P4 | “the app said so” | no | no | **fail** |

P1 is the only reason that works **before the names exist**.
That is how a program can say “possible” and still be doing
mathematics: sixteen (or any \(X>6\)) typed slots, four
couplings plus Planck and \(\Lambda\). It is not a pass on
unification.

## How can it come up with \(X\) candidates?

| id | Reason | Verdict |
|---|---|---|
| X1 | type every object in a catalog; keep allowed types; \(X=\lvert\mathrm{survivors}\rvert\) | open — this is the one that matches “it already knew harmonic / gauge / topological” |
| X2 | \(X=\) dimension of a moduli / leftover space | open |
| X3 | \(X=\) knobs on a screen | open — we do not have the screen |
| X4 | pick a round number | **fail** |

X1 does **not** need \(F\). It needs a catalog and a type
map. Cosmos 3-D already had the type map. That is enough to
emit a list and a count. “Candidate” means *type-correct and
allowed in the domain (or as a must-hit leftover)*. It does
not mean *succeeds*.

## The reconstructed enumerator

On the 4×4 sixteen we already have (still not the Cosmo
export):

- \(X_{\mathrm{eligible}}=15\) (everything except \(R\), which is the output)
- \(X_{\mathrm{must\ hit}}=7\) (four couplings + QCD scale + Planck + vacuum)
- \(k_{\mathrm{nature}}=6\)
- \(15>6\), so **possible-by-count is true**

Drop any one type (gauge, gravity-gauge, topological,
harmonic, or teleological). \(X\) stays above 6. So the
“possible” sentence is robust to a missing finger. That is
why a program can keep saying possible even while it argues
about which types belong.

## “Able to do it”

The app can know they are **candidates** without knowing they
**work**.

Able, here, means: typed correctly, and there are enough of
them. Not: \(F\) hit \(\alpha_{\mathrm{em}}\). Affine \(F\)
on this vector already failed. P3 is fail. P1 stays open.

If the Cosmo export includes its own type tags, replace the
open type list and re-count \(X\). Do not treat the count as
\(F\).
